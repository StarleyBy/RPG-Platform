# RPG Platform — Manifest Editor

Веб-редактор манифестов для универсального RPG-движка: экипировка,
материалы, существа, локации, классы, профессии, способности — всё в
едином, взаимосвязанном наборе JSON-манифестов. Один статический
HTML-сайт, без сборки, без бэкенда — редактирует файлы либо напрямую на
диске (File System Access API), либо прямо в GitHub-репозитории (REST API).

## 1. Структура проекта

```
index.html                    входная точка — только разметка, стили и
                               скрипты подключены отдельными файлами

css/
  editor.css                  все стили редактора

js/
  ru-dict.js                  словарь переводов enum-значений на русский
  utils.js                    STATE, пути, мелкие утилиты (el(), toast()...)
  adapters.js                 LocalAdapter / GitHubAdapter — источники данных
  bootstrap.js                загрузка схем/манифестов, проверка ID, навигация

  fields/
    basic-fields.js           string/int/float/range/bool/enum/tags/formula
    ability-list-field.js     конструктор способностей (verb:target:...)
    reference-fields.js       manifest_ref / manifest_multiref / vocab_multiselect
    level-track-field.js      прогрессия по уровням (профессии/классы)

  pages/
    editor-page.js            выбор категории → форма создания/правки
    database-page.js          поиск, фильтры, статистика по всем манифестам
    dashboard-page.js         сводка по категориям + детектор битых ссылок

  settings.js                 диалог источника данных, инициализация

data/
  schemas/                    ⭐ ГЛАВНАЯ БАЗА ДАННЫХ — одна JSON-схема на
                               каждую категорию (оружие, классы, профессии...)
  vocab/                      открытые словари (материалы, расы, фракции,
                               типы оружия/брони, damage-типы...)

                               наполнения через таблицы (см. его README)
```

### Как запустить

```bash
python3 -m http.server 8000
```
и открыть `http://localhost:8000`. Двойной клик по `index.html` (`file://`)
не сработает — File System Access API и `fetch()` к GitHub требуют https
или localhost. Так же работает через GitHub Pages без каких-либо изменений.

## 2. Почему стили и скрипты вынесены отдельно

Раньше всё жило в одном HTML-файле — это было нормально, пока редактор
был маленьким прототипом. Сейчас в проекте 35 схем и своя логика для
7 типов полей — держать всё в одном файле означало бы либо бесконечный
скролл при любой правке, либо конфликты при параллельной работе над
разными частями. Разбивка построена по функциональным границам, а не
произвольно:

- `fields/` отделены от `pages/` — типы полей не знают, на какой они
  странице, страницы не знают, как устроен рендер конкретного поля.
- Порядок подключения `<script>` в `index.html` важен (это классические
  скрипты в общем пространстве имён, не ES-модули — сознательный выбор,
  чтобы не требовать сборщика и не усложнять локальную отладку). Каждый
  следующий файл использует то, что объявили предыдущие.
- `ru-dict.js` — самый большой файл (910 переводов) — вынесен первым и
  отдельно, чтобы будущие правки перевода не задевали логику рядом.

## 3. Главное: живые перекрёстные ссылки вместо свободного текста

### Проблема, с которой всё началось

Поле "Ограничения по классам" у оружия раньше было обычным текстовым
полем: впиши класс(ы) через запятую. На практике это означает, что один
человек введёт `вор`, другой `плут`, третий `ассасин` — три разных
строки для одного и того же по смыслу класса, и предмет в игре либо
станет доступен не тем, либо не тем, кому нужно, недоступен. Опечатка
`воинн` вместо `воин` — тот же эффект, только тише: работать будет,
просто предмет никто и никогда не получит.

### Решение: новый тип поля, который знает про остальной проект

Раньше все выпадающие списки в редакторе читали *статичный* словарь
(`data/vocab/*.json`) — конечный список готовых значений, зашитый на
момент написания схемы. Для рас, редкости, типов урона это нормально:
такие списки меняются редко и осознанно.

Но классы, профессии, способности — это открытые, растущие сущности
самого проекта: их создаёт тот же человек в том же редакторе. Поэтому
появилось **три новых типа поля**, которые вместо статичного словаря
читают **живое состояние `STATE.manifestIndex`** — то есть другие уже
существующие манифесты:

| Тип поля | Что показывает | Где реализован |
|---|---|---|
| `manifest_ref` | одиночный выбор из манифестов заданного типа | `js/fields/reference-fields.js` |
| `manifest_multiref` | мультивыбор (чекбоксы) из манифестов заданного типа, можно сразу нескольких типов с группировкой | там же |
| `vocab_multiselect` | мультивыбор (чекбоксы) из статичного словаря — та же UI, что у manifest_multiref, но источник — `data/vocab/`, а не другие манифесты | там же |
| `level_track` | повторяемый список "уровень → что открывается" (способности + ресурсы), сам внутри использует `manifest_multiref` | `js/fields/level-track-field.js` |

Опечатка теперь физически невозможна: либо нужный класс уже существует
и появляется чекбоксом в списке, либо его ещё нет — и поле честно
показывает "Пока нет ни одного подходящего манифеста — сначала создай
хотя бы один", а не принимает произвольный текст.

### "Живость" — форма не замораживает список на момент открытия

У каждого `manifest_ref`/`manifest_multiref`-поля есть кнопка
**🔄 Обновить список**. Она заново перечитывает все манифесты (через тот
же адаптер — диск или GitHub) и перестраивает варианты **прямо в уже
открытой форме**, не сбрасывая остальные введённые значения. Это ровно
твой сценарий: два дня назад для "Шахтёра" было доступно 2 руды, сегодня
добавили ещё 3 — жмёшь "Обновить" в поле профессии, и все 5 сразу видны,
без пересоздания формы с нуля.

### Начали с "элементарных частиц", как ты и предлагал

Три новые схемы в группе **🧩 Базовые элементы**:

- **`ability.json`** — каталожная способность (не путать с произвольными
  эффектами `ability_list` внутри предмета — там разовый авторский
  эффект конкретной вещи, здесь именованная переиспользуемая сущность,
  на которую можно ссылаться из классов/профессий/существ).
- **`character_class.json`** — класс: владение оружием/бронёй
  (`vocab_multiselect` из вынесенных `weapon_subtypes.json`/
  `armor_classes.json`), набор способностей (`manifest_multiref` →
  `ability`), врождённые сопротивления/уязвимости, связь с фракциями.
- **`profession.json`** — прогрессия 1-25 уровня (`level_track`): что
  открывается на каждом уровне (способности + доступные для добычи/крафта
  ресурсы) плюс формула растущего бонуса (`chance_formula`, например
  `0.005 * max(0, PROFESSION_LEVEL - 5)` — для "шанс побочной добычи
  растёт после 5 уровня, а на 21-25 даёт несоразмерно много").

Пример именно твоего "Шахтёра": создаёшь материал "Серебряная руда" →
создаёшь профессию → добавляешь строку уровня "5" → в поле "Открывает
добычу/крафт ресурсов" видишь и выбираешь уже существующую руду. Позже
добавил руны — жмёшь "Обновить список" в той же строке, руны появляются,
дополняешь профессию, не трогая остальное.

### Что переведено на новые поля прямо сейчас

`class_restrictions`/`race_restrictions`/`faction_restrictions` у
`weapon.json`, `armor.json`, `accessory_artifact.json`,
`blueprint_recipe.json`, и `factions_present` у
`continent_region_biome.json` — это шесть самых очевидных мест, где
свободный текст был прямой угрозой согласованности. Остальные 29 схем
пока не тронуты намеренно — не потому что там нет похожих полей, а
чтобы не переделывать всё разом без обратной связи. Дальше — по одной
категории за раз, начиная с того, что реально понадобится раньше.

## 🧭 Дашборд — третья страница

Помимо Редактора и Просмотра/базы данных — третья вкладка:

- **Сводка по категориям**: карточка на каждую из 35 схем со счётчиком —
  клик открывает категорию в Редакторе.
- **Проверка целостности ссылок**: сканирует все `manifest_ref`/
  `manifest_multiref`-поля во всех манифестах и находит "битые" ссылки —
  ID, на который что-то ссылается, но которого больше нет (удалили класс,
  а оружие всё ещё на него ссылается). Список кликабелен — сразу
  открывает проблемный манифест на редактирование.
